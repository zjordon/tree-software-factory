## 一句话定义

围绕 AI-native SDLC 的**一人接单工作室**：客户自助说出需求，工厂七站流水线把它加工成"软件 + 完整出处链 + 持续维护"；树哥是唯一人类，只出现在五个判断点上。

## 定位决策（已定型，2026-09-28）

| 决策项 | 内容 |
|---|---|
| 形态 | 一人接单工作室（自用流水线 / 接单工作室 / 产品化平台三形态中选定接单） |
| 客户入口 | **web bundle 自助聊为主**，树哥中转为备选；两条路径必须产出同格式 intent.md（接口不变，只换谁打字） |
| 维护 | **默认含在交付里**：月费复购；spec.md 是"bug（维护覆盖）还是新需求（新订单）"的合同边界 |
| 人员 | **永远只有树哥一个人类**：治理最简（所有门禁签字人都是他），bus factor = 1 |

## 可行性依据

- 三形态判定：自用流水线（高）/ 接单工作室（中高，选定）/ 产品化平台（不建议，Devin/Factory.ai/Lovable 红海）
- 三大硬约束：
    1. **工厂必须制造信任，而不是制造代码**——只优化生成速度的工厂会量产 CrossBeam 形状的软件（每行体面、整体缺一层：IDOR、越权、不能失败的测试）。差异化资产是门禁层，不是生成层
    2. **吞吐天花板 = 验证带宽**——"只在审查跟得上时增加会话"。浏览器验证是树哥主场，也是唯一可能建立的真实壁垒
    3. **判断层不能外包**——工厂产品化的是树哥的判断力（固化成 skill/hook/eval 无限复用），不是他的缺席

## 工厂全景：七站流水线

以典型单子为例（连锁健身房"会员在线预约 + 到店核销"工具）：

| 站 | 产物 | 机制 | 人类判断 |
|---|---|---|---|
| 0 筛单 | 接/不接 + 定档 | agent-business-fit 四步判断法（路径可模板化/失败成本可控/验收标准清晰）+ right-sizing（小改动直达 build） | ✅ 判断 #0：兼产能控制——这单会不会吃掉两周 |
| 1 需求入口 | intent.md | 客户在 web bundle 里自助聊（预埋分析师提问模板 + "够好了才许提交"检查清单），提交到仓库 intent/ 目录 | ✅ 判断 #1：审"他要的是不是他说的"，此刻改方向成本是一页文档 |
| 2 设计 | spec.md | /speckit-specify 加载工作室 skills（技术栈红线/安全基线/UI 规范），标记关注点；UI 给客户看 mock | ✅ 判断 #2：对照 intent 审 spec，开放问题去问客户 |
| 3 计划 | plan.md | plan mode 出计划：改哪些文件/顺序/风险/证明方式 | ✅ 判断 #3：拷问计划（哪步最易翻车/没选的方案），批准即装配指令 |
| 4 构建 | diff + tests | 自动模式按 plan.md 实现；会话内反馈回路（build/test/lint）先自检；hooks 无声值守（修 bug 禁改测试文件/冻结区拦截/密钥拦截）；独立任务 worktree 并行 | —（人可以不在场） |
| 5 验证 | 证据链 | **自研层**：浏览器验证 agent（TreeWalker 一族）真人式走关键路径逐步截图；AI 第一道审（REVIEW.md 三 pass：bug/安全/合规，对照 spec/plan 查"是否做了计划要做的事"） | ✅ 判断 #4：核心质检——读发现清单+证据链而非每行；安全项（认证/越权/数据隔离）亲自看 |
| 6 交付 | 上线 + 交付包 | 部署走白名单工具；发布 hook 请求授权；交付包 = 软件 + 整条产物链 + 交接文档 + 维护条款 | ✅ 判断 #5：授权发布 |
| 7 维护 | 闭环 | 健康信号进控制带（出厂项目预埋日志/指标埋点）；事故自动写成新 intent.md 重入管道；每次修复沉淀一条 eval | —（分诊例外） |

目标量级（非承诺）：此单传统小外包 3-6 周；工厂路线一周上下，其中树哥纯投入一两天（五个判断点合计，通常不足整单工时三分之一）。

## 三个定位决策的设计推论

**自助前台**：
- intent.md 质量取决于打包进 web bundle 的提问模板，不是中转追问——bundle 是要设计的第一个产品面，垃圾进不去
- 判断 #1 变异步：早上审昨晚客户自己产出的意图；时间从"接洽"挪到"把关"
- 中转备选产出同格式 intent.md，客户懒不懒得聊不影响工厂内部

**维护含在交付**：
- Stage 6/7 从"售后"变成"产品本体"：每个出厂项目必须带健康信号端口，仓库模板从第一天预埋日志/指标埋点
- 合同边界用产物链仲裁：spec.md 写了的是 bug（维护覆盖），没写的走新 intent（新订单）——可原样写进合同
- 经济形态订阅制：月费 + 每次事故沉淀 eval，单项目维护成本随时间下降

**永远单人**：
- 好处：治理全简化，零交接损耗；对客户是卖点——"一个可追责的人 + 完整审计轨迹"比"团队做单但人员流动"更可信
- 代价一：AI 独立上下文初审是**唯一存在的第二双眼睛**，验证层不能省
- 代价二：产能无"加班同事"，筛单兼产能控制
- 设计回应：产物链保证**任意一单在任意一站可停机、冷却、再开机**——没有半成品烂在人脑子里，订单进度都在最后一份 committed artifact 里

## 贯穿三条线

1. **产物链 = 传送带 = 审计轨迹 = 销售资产**：intent→spec→plan→PR→审查发现→eval 结果，既是站间接口，也是给客户的信任凭证（对 AI 产出有信任焦虑的企业客户，"每一行都有出处"就是产品本身），还是出问题时还原"当时想要什么"的依据
2. **飞轮：每接一单工厂变强一点**：每单沉淀 skills/模板/evals，同类需求 build 时间砍半（D2C 调研的"CRUD 模板降维"是前身）。私活只产出代码，工厂还产出产能
3. **瓶颈从打字移到审查，审查被验证层杠杆放大**：这是"单人质检"能撑起一座工厂的原因

## 技术组装路线（依据 [[ai-software-factory-landscape]]）

- **骨架**：spec-kit（~139k★，GitHub 官方）或 OpenSpec（偏轻量存量项目）承担 Plan→Build 三站
- **客户入口**：BMAD web bundle（Gemini Gems / ChatGPT GPTs）改造为工作室版（自烘提问模板）
- **自研后半本**（开源版图空白段，工厂的核心资产）：hooks 门禁、evals、REVIEW.md、浏览器验证器 agent（TreeWalker/web-gui-tester 一族）
- **Maintain**：参考 Cloudflare×Astro 的 issue 工厂 + ADLC（Agents + Agent Traces）思路
- **不要自己发明前半本**；claude-flow（73.4k★）仅借鉴 SPARC 阶段化质检与跨会话记忆思路，不全盘采用（过重）

## 供应链纪律（从第一天开始）

gpt-pilot 事件：33.7k★明星项目停维护，且 2025-08 至 2026-06-11 间 core/telemetry/ 被植入偷凭据蠕虫。教训：工厂自身会成为攻击面——依赖锁定版本、来源白名单、定期轮换凭据；选开源件先看维护状态。

## go/no-go 与首条产线原则

- 试点交付量三个数：intent.md 提交到上线总时长（先行）、第一次实现就合并的变更份额（先行）、返工周期数 + 交付后两周内事故数（滞后）
- 不达标时问题几乎一定出在验证层而非生成层——加固门禁，不换更大的模型
- **第一条产线必须同时是第一个真实交付物**：工厂 v1 = 这次交付实际用到的东西；用交付养工厂，不是先建厂再找活
- 采纳路径照抄手册："起初手工为每一步发提示；终态是一个回路"——手工作坊跑通三次，再固化 skill，最后上自动触发

## 这不是什么

- 不是"客户输入需求，机器无人参与吐出软件"——那是 vibe coding 工厂，量产 CrossBeam
- 不是"用 AI 写代码"的现状加速版——区别在于工序间以 committed artifact 为接口、判断被固化成 skill/hook/eval，产能随订单数增长而不随工时增长
- 交付物不只是软件——是"软件 + 证据链 + 可持续维护"
